# The remote: controlling the show over SSH

The show has a remote control. It is a terminal program on the Pi, reached over SSH, that
looks like what a TV remote would look like if it were made of text: big LED digits for the
channel, the programme grid, a progress bar, and the usual buttons. Anyone with a key can zap;
admin keys can also upload and delete *visuals*, scenes written in C that join the loop as
channels 30 and up. Nothing here needs sudo and nothing opens a new port: it is sshd, a
dedicated user and one dispatcher script.

```
ssh zapper                      the zapper (below)
ssh zapper 7                    channel 7, held until the next command
ssh zapper next | auto          skip | back to the loop
ssh zapper play testcard 30     show something once, for 30 s
ssh zapper status | list | log
ssh zapper upload foo < foo.c   admin: a new visual, channel 30+
ssh zapper rm foo | fetch foo   admin: delete | download the source
```

`scripts/tv` wraps this for your own machine: `tv`, `tv 7`, `tv upload foo.c`, and
`tv config host <ip>` when the Pi has no alias (below).

## Channels

| Channel | What | Where it comes from |
|---|---|---|
| 00 | standby, a black picture | `src/scenes/black.c` |
| 01–17 | the loop, in play order | `scene_loop[]` in `src/scenes.c` |
| 20–22 | extras: `explain`, `stack`, `testcard` | `scene_extra[]` |
| 30–61 | uploaded visuals, alphabetical | `visuals/*.c` on the Pi, table generated by `tools/gen-visuals.sh` |

Three modes: **auto** plays the loop, **hold** repeats one channel (that is what a channel
number does), **once** shows a channel one time and returns to the loop (`play`). Every change
goes through the normal fade.

The remote always switches the show on, as on a TV set: systemd holds the control socket open
(`bc101.socket`), and the first command that arrives starts the show if it is not running.
`systemctl stop bc101` is standby; `systemctl stop bc101.socket` unplugs it, the show goes off
with it and the remote answers `show not reachable` until `systemctl start bc101.socket`. That
is the way for maintenance, or for anything else that wants the framebuffer and tty1.

## The zapper

```
  tvtv ▸ ZAPPER  · alice (admin)                                      ● 13:37:05

  █▀▀█ ▀▀▀█   PLASMA  loop               HOLD   bis n oder Enter
  █  █    █   ██████████░░░░░░░░░░░░░░░░░░░░░░░░░░   2.8 s / 10 s
  ▀▀▀▀    ▀   50.0 fps · worst 17.1 ms · on air 2h04m

  PROGRAMME · 21
  00 black      05 explode    10 tunnel     15 outrun     22 testcard
  01 boot       06 kaleido    11 matrix     16 crt
  02 flowers   ▸07 plasma     12 juggle     17 bernd
  …
 0-9 Programm  ↑↓ zappen  Enter halten/auto  n weiter  i info  ? hilfe  q ende
```

| Key | |
|---|---|
| `0`–`9` | channel, two digits like on a TV set (one digit: 1.5 s, or Enter) |
| `↑` `↓` `+` `-` | zap through the channels |
| `Enter`, `Space` | hold this channel; again: back to auto |
| `n` / `a` | next / auto |
| `i` | fps per channel (what `/run/bc101/anim.log` holds) |
| `x` | delete the visual on air (admin, asks first) |
| `u` / `?` / `q` | upload hint / help / quit |

It is plain ANSI, 16 colours and UTF-8 block glyphs, so it works in any terminal, including
an SSH app on a phone. `tvctl remote --ascii` for terminals without the glyphs.

## Setup, once

Three accounts take part on the Pi, and keeping them apart is most of the setup:

| Login | Who | Rights |
|---|---|---|
| your own | a person | sudo with a password; needed once, for the setup |
| `deploy` | the deploy automation (`scripts/deploy.sh`, `tv-keys`) | exact sudo rules, no password; written by the setup |
| `zapper` | the remote | no shell, the dispatcher only, keys only |

The setup needs root once, and only a person has that: the deploying login has no password and
no sudo for arbitrary commands, so the root step cannot run over a plain `ssh`. Hence two steps:

```sh
scripts/deploy.sh --setup        # 1. workstation: syncs a copy and prints the command below
ssh you@<the pi>                 # 2. the Pi, as yourself:
sudo ~deploy/tvtv-setup/tools/setup-remote.sh --deployer deploy
```

`BC101_SETUP_HOST=you@<the pi> scripts/deploy.sh --setup` does both in one go, with sudo
asking for your password in the terminal. `tools/setup-remote.sh` is idempotent, run as root,
and does this: creates the system user `zapper` (groups `video`, `tty`; `TVTV_USER` picks
another name, and a name that belongs to a person is refused, because the sshd rule below
would lock that person into the dispatcher), moves the show to `/opt/tvtv` owned by `zapper`,
installs the dispatcher as `/usr/local/lib/tvtv/tv-dispatch`, `tv-keys`, the empty keys file
`/etc/tvtv/authorized_keys`, the sshd drop-in `system/sshd-tv.conf` (checked with `sshd -t`,
then reloaded) and the systemd unit, writes `/etc/sudoers.d/tvtv-deploy` for the deploying
login (`rsync` and `make` as `zapper`, the unit file from stdin, `systemctl` for the service,
`tv-keys`, mounting and unmounting the USB stick `/dev/sda1` on `/mnt` by hand), adds the
stick to `/etc/fstab` as an automount (see Doom below), and runs `tools/install.sh` (build as
`zapper`, restart, health check). From then on plain `scripts/deploy.sh` targets `/opt/tvtv`
without prompts. A change to `tools/tv-dispatch` reaches `ssh zapper` only through the setup
again: sshd runs the root-owned copy. The old checkout in the
deploying login's home can go.

Then your key and an alias. Use the Pi's IP address if its host name does not resolve from
your machine:

```sh
ssh-keygen -t ed25519 -f ~/.ssh/id_ed25519_zapper -N ''
ssh tvtv-deploy sudo tv-keys add alice admin < ~/.ssh/id_ed25519_zapper.pub
```

```
Host zapper
    HostName <the pi>
    User zapper
    IdentityFile ~/.ssh/id_ed25519_zapper
```

Or no alias at all: `scripts/tv` keeps its own settings in `~/.config/tvtv/remote`
(`$XDG_CONFIG_HOME/tvtv/remote` if that is set).

```sh
scripts/tv config host 192.0.2.10
scripts/tv config user zapper
scripts/tv config identity ~/.ssh/id_ed25519_zapper
scripts/tv config                       # shows them; an empty value unsets a key
scripts/tv --host 10.0.0.9 status       # one call elsewhere
```

The address comes from `--host`, else `TV_HOST`, else the settings, else the alias `zapper`.
`user` and `identity` apply to every address: without them, `--host` logs in with your own
login name and keys, which `zapper` does not accept.

`scripts/tv status` answers `ok` and the current scene; `scripts/tv` opens the zapper.

Keys: `tv-keys add <who> <op|admin> [file]`, `tv-keys rm <who>`, `tv-keys list`. `op` zaps,
`admin` also uploads and deletes. Every command is logged with the key's name:
`journalctl -t tvtv`. The show runs on one core; an open SSH session costs it some of that, so
a few long frames while the zapper is open are the price of the remote, not a bug.

## A new player

Every device that steers the show gets its own key and its own name. A name holds one key:
`tv-keys add` with a name that exists replaces that key, so a second laptop of the same
person is `alice-laptop`, not `alice` again. The log then also says which device zapped.

The player, on the new device (it must reach the Pi: the LAN, or the tailnet with the
bc101 relays' routes; `nc -vz <the pi> 22` tells):

```sh
ssh-keygen -t ed25519 -f ~/.ssh/id_ed25519_zapper -N '' -C <name>
cat ~/.ssh/id_ed25519_zapper.pub          # this line goes to an admin; it is not a secret
```

An admin, from a machine with the deploying login, picks the role (`op` zaps, `admin` also
uploads and deletes) and adds the key:

```sh
ssh tvtv-deploy sudo tv-keys add <name> op < <name>.pub
ssh tvtv-deploy sudo tv-keys list         # name, role, fingerprint
```

The player again: the alias block above in `~/.ssh/config`, or `scripts/tv config` with
host, user `zapper` and the key. Then `ssh zapper status` answers `ok`, and `ssh zapper` opens
the zapper. A key that is not on the list gets `Permission denied (publickey)`.

To take a player off: `ssh tvtv-deploy sudo tv-keys rm <name>`; the next login fails with
`Permission denied (publickey)`. A zapper that is open at that moment keeps working until it is
closed, on purpose: the remote in someone's hand does not die mid-zap.

## Visuals

A visual is a scene like the ones in `src/scenes/`: a file that includes `core.h` and ends in
`const Scene scene_<name> = {"<name>", seconds, init_or_NULL, frame, NULL};`. The name is the
channel's name: lower case letters, digits and `_`, up to 16 characters, starting with a letter,
not one of the built-in names. `docs/demo.c` is a small one to try. `tv upload foo.c` sends it
(at most 256 KB); on the Pi it is

1. checked (text, size, the `scene_<name>` definition),
2. compiled with the show's flags (`make`, the compiler's complaints come back to you),
3. run offscreen through its whole length with `build/preview … bench` (a crash, a hang or
   more than 60 ms per frame is a rejection; the budget on air is 20 ms),
4. linked into a new `bc101`, which the running show `exec`s after its fade, keeping the
   channel and mode it was on. If the new build does not answer within seconds, the previous
   binary (kept as a hard link) goes back and systemd restarts it.

`tv rm foo` deletes the source and rebuilds the same way; `tv fetch foo > foo.c` downloads it
first if you want to keep it. Visuals are state on the Pi, not part of the repo; a deploy
leaves `visuals/` alone.

## What is and is not protected

- The user `zapper` can run exactly one program, the dispatcher, with a key only: `ForceCommand`,
  `AuthenticationMethods publickey`, no forwarding, no `~/.ssh/rc`. The keys file, the sshd
  drop-in and the dispatcher are root-owned; sshd names the key that logged in
  (`ExposeAuthInfo`), and the dispatcher takes the role from that line.
- The dispatcher parses the command with a whitelist (letters, digits, space, `.`, `_`, `-`,
  at most 80 characters) before anything else happens; names and numbers are checked against
  patterns; nothing is passed to a shell.
- The show runs as `zapper`, not root, inside a systemd sandbox: no network, read-only file system
  including its own directory, only `/dev/fb0` and `/dev/tty1`, no new privileges, a syscall
  filter (`systemd-analyze security bc101` says 0.8, SAFE). That is the real protection
  behind uploads: a visual is code, and code from an admin key runs as `zapper` with exactly
  those rights.
- An admin key therefore means: can run code as `zapper` on the Pi. There is nothing else on the
  Pi worth having, but hand admin keys out accordingly, and `tv-keys rm` when in doubt.
- The dispatcher's own client is `tvctl`, built without scene code, so a visual cannot take
  down the hand that controls it; the health check uses it too.
- The deploy path does not lead from `zapper` to root: the unit file is rendered on the
  workstation and sent as is, the deploying login may only run `rsync` and `make` as `zapper`
  plus fixed `systemctl` commands, and the setup refuses to run from a tree `zapper` owns. What
  remains is that a visual's test run happens outside the sandbox, as `zapper`; a process it
  leaves behind has `zapper`'s rights and nothing more.
- Doom is the exception to "op only zaps": any key starts a 1993 C engine as `zapper`, outside
  the sandbox, fed with that key's keystrokes and a WAD from the list below. A bug in the
  engine is therefore as far as an op key reaches: `zapper`'s rights, like an admin key.

## Doom

```
ssh -t zapper doom                      Doom's title and menu: new game, episode, skill
ssh -t zapper doom freedoom1 e1m3 4     straight into a level (e1m1..e4m9, map01..map32), skill 1-5
ssh zapper doom list                    the games on the USB stick and in /usr/share/games/doom
```

A name on both is taken from the stick; only games (IWADs) are listed, not add-ons. The stick
(vfat, `/dev/sda1`) mounts on `/mnt` when something looks there and unmounts after a minute
idle, so it can be pulled; the setup writes that line into `/etc/fstab`. Without a stick a
look at `/mnt` waits up to 2 s for it, so `doom` starts that much later.

In the zapper, `d` starts Doom's menu. The picture goes to the TV, the keys come from your
terminal, so the terminal needs `-t`. The show hands the screen over (`yield`, see
`src/main.c`) and takes it back when Doom ends: Ctrl-C, Doom's own quit, an engine error, a
lost connection (once sshd notices, up to two minutes; in a kitty terminal a key that was held
stays held until then), or anybody zapping a channel meanwhile (that ends Doom: SIGTERM,
SIGKILL after 2 s; settings changed in that game are not saved then, savegames are). The
zapper shows DOOM meanwhile. A level must be in the WAD:
`e1m1` for Doom 1 games like freedoom1, `map01` for Doom 2 ones like freedoom2 (the dispatcher
reads the WAD's directory).

| Key | |
|---|---|
| arrows, `w` `s` | walk and turn |
| `a` `d` | strafe |
| space, `f`, Ctrl | fire |
| `e` | use: doors, switches |
| Shift (or `r`, a toggle) | run |
| Alt | strafe with the arrows |
| `1`–`7`, Tab, Esc | weapons, map, menu |
| Ctrl-C | quit |

Terminals send key presses, not releases. Doom asks the terminal for the kitty keyboard
protocol (kitty, Ghostty, WezTerm, foot, Alacritty, recent iTerm2); one that speaks it reports
releases and lone Ctrl/Shift/Alt, and Doom plays like on a keyboard. Elsewhere (macOS
Terminal, PuTTY) a movement key counts as held until it stops repeating: 0.55 s after the
first press, 0.12 s after a repeat; tap twice for short steps. Letters still type, so cheats
and savegame names work. Doom puts the terminal back as it was when it ends or gets SIGINT,
SIGTERM or SIGHUP; after a crash `reset` does it.

The engine is `third_party/fbdoom` (Chocolate Doom for a plain framebuffer, GPL-2.0-or-later,
our changes on top, see `ORIGIN`), built by `make` as `fbdoom`. It stretches 320x200 over the
720x288 picture, keeps its settings and saves in `/opt/tvtv/doom/.fdoom.tar/` and logs to
`/opt/tvtv/doom/fbdoom.log`. It runs as `zapper` in the SSH session, outside the show's
sandbox, with the framebuffer through the group `video`; any key may start it. A WAD is data
for a 1993 engine that trusts it: one from the stick runs with `zapper`'s rights at worst, so
only put WADs on the stick you would also run.

## For developers

`bc101 -x -s /tmp/ctl` runs the show headless with a control socket; `tvctl -s /tmp/ctl status`
or `bc101 ctl …` talks to it; `tvctl remote -s /tmp/ctl` is the zapper against it, and
`--frame` prints one picture (tests, screenshots). Protocol: one line per connection, the reply
starts with `ok` or `err`, then payload lines. `tests/ctl.bats` and `tests/dispatch.bats`
cover sequencer, socket, dispatcher, roles, injection attempts, upload, rejection and rollback;
they run on any Linux box with `make`, `bats` and `ssh-keygen`.
